foc Project Documentation

Introduction

foc is a field-oriented-control library for three-phase PMSM drives. One engineering constraint drives every design choice: the control loop must be predictable — no heap, no exceptions, no virtual calls, no hidden allocation in the code path that runs every PWM period.

Three consumer faces share one implementation:

表 1 One core, three faces

Face

Header / module

Who it is for

C++17

foc/motor/motor.hpp

Board-level users: inject your own HalPolicy and own every gain.

C11

foc/api/foc_api.h

Non-C++ projects, glue code and scripted tests: a frozen ABI over the same core.

Python

import foc_python (optional)

Host-side scripts and data analysis, built on the C API.

What V1 does

  • Clarke / Park and their inverses, space-vector modulation, PI controllers, a motor state machine and a back-EMF observer.

  • Policy-composed motor: observer, modulator, controller and HAL are template parameters, so the whole current loop inlines into one translation unit.

  • Simulation-grade HAL stubs (PWM duty history, scripted current, simulated position), so the complete control chain can be exercised without hardware.

  • A C API with generation-checked opaque handles: a stale handle is detected, never dereferenced.

  • An optional pybind11 module that binds the C API, not the C++ templates.

All of this is verified in software only — see honest limits.

Project structure

foc/
├── include/foc/     # public headers: core / hal / driver / motor / api
├── src/             # implementation, paired one-to-one with the headers
├── api/             # pybind11 bindings (compiled only when enabled)
├── test_package/    # Conan test package: unit, stress, pure-C and Python consumers
├── metadata.json    # single source of truth for the build switches
└── docs/            # Doxygen + Sphinx pipeline (this site)

Honest limits

V1 does not claim, and does not pretend to verify, the following. They are deferred to the hardware stage. (For the limits that are not deferred -- the ones that are properties of the method and are pinned by test cases -- see what this library does not do.)

Item

Why it cannot be verified yet

Dead-time compensation in practice

Needs the real inverter non-linearity.

ADC sampling aligned with PWM timing

Depends on the MCU timer and trigger chain.

Observer robustness against real parameter drift

The perturbation used in the SIL model is idealised.

EMI / EMC behaviour

Not observable in software.

Acoustic noise and vibration

Needs a mechanical load.

ISR worst-case execution time on the target MCU

No target profile is shipped.

Flash / RAM footprint against a chip budget

No target constraint to measure against.

A pure-C consumer without the C++ runtime

Would need a stripped link script and hand-written stubs; V1 explicitly requires C users to link the C++ runtime.

What has actually been run

Three sentences, because each is a different claim and only the first is evidence:

  • Verified: x86-64 Linux, gcc 13, the unit suite plus the SIL plant. Every number in this documentation comes from that combination, and Reproducing these numbers is the list of commands that produces it.

  • Cross-compiled: aarch64 and Cortex-M targets compile and link -- that is what the cross-compile check proves. It proves the code builds for the architecture. It does not prove the code runs there, and nothing here should be read as if it did.

  • Not run: no target board has executed this library. Not one measurement, in or out of the suite, was taken on silicon.

The gap between the second and the third sentence is where a porting project does its work: the Porting the library to a board page lists what a board must answer, and its minimal example is compiled but never executed on hardware either. A statement about a machine is a statement about that machine, and it belongs to whoever brings the board.
