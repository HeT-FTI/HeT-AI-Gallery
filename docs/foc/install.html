2. Installing and toolchains

Quick start is the short path: four steps to a running loop. This page is the reference behind step 1 and step 2 — the matrix, the three ways to consume the package, and the link errors that mean you have it almost right.

Nothing on this page needs Sphinx or Doxygen: those build this documentation, not the library.

2.1. What the build needs

The floors are in metadata.json, not in this page — the table repeats them so that a reader can see the whole picture at once, and metadata.json stays the one place they are declared:

Library dependencies come in three buckets, and only one of them reaches a device build:

  • core — etl (fixed-capacity containers, header-only). This is the only dependency on the bare-metal whitelist.

  • test — GTest. Host only.

  • bindings — pybind11. Host only, and skipped automatically on a cross build.

2.2. Three ways to consume it

Two of them end at the same link line, which is the point: one aggregate target carries both component targets and the package metadata guarantees their order.

You have

Do

Then

Conan

self.requires("foc/0.1.0") in requirements()

find_package(foc REQUIRED) + target_link_libraries(app PRIVATE foc::foc)

A prebuilt or locally installed package

put the Conan generator folder (or the install prefix) on CMAKE_PREFIX_PATH

the same find_package and the same foc::foc target

The repository itself

add_subdirectory(foc)

the in-tree targets are foc_c, foc_cpp and the aggregate foc. The foc:: namespace is added by the exported package config, so it does not exist in this case

Link the aggregate target and not foc_c alone unless you know why: the aggregate is what the package's own tests use, and it is the only one whose ordering is guaranteed.

2.3. The C consumer's link failure

A C program can use the C ABI and still has to link the C++ runtime:

add_executable(app main.c)
set_target_properties(app PROPERTIES LINKER_LANGUAGE CXX)   # without this: __cxa_*
target_link_libraries(app PRIVATE foc::foc)

Without LINKER_LANGUAGE CXX (or one empty .cpp in the target) the link fails with symbols named __cxa_ — the C++ runtime's own entry points. That is not a packaging accident: the ABI is C, the implementation is C++, and the library says so instead of hiding a C++ runtime behind a C header. The pure-C row in honest limits is the stronger version of the same statement — a C consumer without the C++ runtime is explicitly not supported.

2.4. Common failures, and what each one means

Symptom

What it is

a link error naming __cxa_ symbols

the C target is being linked as C; set LINKER_LANGUAGE CXX

foc::foc target not found

the Conan generator folder is not on CMAKE_PREFIX_PATH, or find_package was called before conan install ran

import foc_python fails

the bindings are host-only and off on cross builds; check metadata.json → enable_python_bindings, and put the built module's directory on PYTHONPATH

the library compiles but a policy does not

the motor is policy-composed: an observer or modulator that does not model the required concept fails at instantiation, with the concept name in the error

-Werror fails inside the library headers

the headers are built with the project's own warning set; a consumer's stricter set can differ. Open an issue rather than silencing it — the headers are meant to be clean

the doc build fails on doxygen

documentation tooling is separate from the library; the site needs a loadable doxygen and sphinx but a consumer never does

Two qualifications, both of them about what a check mark does not mean:

2.6. Platforms

Platform

What is actually covered

Desktop -- Windows, Linux, macOS

each is a build-and-run leg, which is what the table above records

Cortex-A Linux -- arm-linux-a53

a cross build with the Python bindings skipped, and the pil gate replaying one scenario on the target ISA under qemu

Cortex-M bare metal -- mcu-m4, arm-none-eabi

a cross build and a link; no execution, because nothing in CI has a board attached

anything else

The numeric domain belongs to the platform rather than being an implementation detail: the library computes in single precision and assumes a single-precision FPU instead of emulating one. On a part without an FPU the same code runs through software floating point and none of the timing figures in this repository apply to it. double appears only where a value is cheaper to keep exact than to re-derive -- the trajectory's position accumulator converts at its exit -- so it is not a second numeric domain, and the _f64 C entry points avoid a narrowing at the call site only. Q31 fixed point is deliberately not implemented; What this library does not do says where that decision comes from.

2.7. Cross builds

Two things change on a cross build, and both are by design:

  • the Python bindings are not built — a target with no Python cannot load them, and pretending otherwise produces a module nobody can import;

  • the tests are not run on the target — they are host tests over the same sources. What cannot be verified without hardware is listed under honest limits.

The worked example is benchmark/profiles/cortex-a7.profile; the same two switches are what a Cortex-M bare-metal profile sets, with etl as the only dependency left in the graph.

2.8. Adding a dependency

Two files, and neither of them is a CMakeLists.txt: the graph is computed from conandata.yml and the package names and targets to link come from the dependencies field of metadata.json. The requirement can be a package archived on Conan Center or one you built yourself -- for the second, you also need a Conan remote that serves it, because a build with no source for a requirement is a build that resolves differently on somebody else's machine.
