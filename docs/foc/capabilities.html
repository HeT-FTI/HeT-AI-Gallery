2. What each capability offers, and what it costs

The boundaries page says what this library cannot do. The README's claim table says what is measured and how it is checked. Neither answers the question the person adding an algorithm actually has: what does a capability have to come with?

This page is that answer, one row per capability. Five columns: the four things a new capability owes, plus the case name that lets the row be audited.

  1. Diagnostic channel -- how the capability says "I am not measuring", "I have not converged", "I am holding". A capability whose only output is a number cannot be debugged in the field, because zero and "no idea" look the same.

  2. Admission -- where a contradictory configuration is refused: at construction or at the first step, never by silently falling back to a default.

  3. Boundary -- the limit, pinned by a case. The cell grammar is fixed and the gate enforces it: a case name in double backticks; or none -- <reason> for "no limit is known", which therefore requires an L3 claim behind it; or na -- <reason> for "this dimension does not apply"; or todo -- <reason> for a hole that is written down instead of papered over. The gate counts the todo rows on every run.

  4. Invariant participation -- which case in test_invariants.cpp this capability must obey. na -- <reason> is allowed and the reason is required.

The capabilities gate checks every cell: a header under core/ or motor/ must be listed here or named in capability-scope.json as deliberately unlisted; every case name must exist as a TEST(); every none must have an L3 claim; every reason must actually be a reason. A row that cannot be filled honestly fails the build, which is the point -- the alternative is a library that grows algorithms and forgets how they fail.

2.1. The three questions a criterion has to survive before it is written down

Not every one of them can be checked by a machine, which is why they live here as prose rather than as a gate. Each is a defect this repository has actually shipped, and each was invisible to the coverage numbers at the time:

  1. Is it vacuously true on the rig I am actually using? The sharpest example: "after hand-over, the angle error is within 0.05 rad in 20 ms" was asserted on a sensored bench, where the loop uses the sensor's angle -- so the error against that sensor is identically zero. The criterion was green, the number was a statement about the bench rather than the capability, and the fix was to delete it and state one that can fail.

  2. Does it only have an upper bound? "must be better than X" alone pushes the next reader to tune until it passes; the honest form also records where a design is expected to be worse. The dead-band ramp is the example: it is worse than a plain sign() step on an ideal step, and that has to be written into the table rather than quietly avoided when tuning.

  3. Does the probe point distinguish the competing formula? Before claiming that a case can reject a wrong formula, evaluate both at that point. sqrt(2ae) against sqrt(ae) was probed at the one place where the two coincide, so the case had no teeth and nothing said so.

2.2. Capabilities that are a procedure rather than a formula

Some of what this library offers is not a law but a procedure: identification of the machine (commissioning.hpp), speed-loop tuning (auto_tune.hpp), learning the cogging table (cogging_learn.hpp). Their criterion is not a constant that could be written into an assertion, so the row records what the procedure owes instead:

  1. It says when it cannot answer. valid == false plus a reason, never a number produced from data that does not describe this machine. A procedure that only answers on good data cannot be claimed for any data.

  2. It states the band it is valid in, in the units the caller measures -- a speed band, a window length, a number of revolutions -- and the band is pinned by a case rather than described in prose.

  3. Its objective is a held-out margin, never accuracy. A procedure optimised for "smaller error" produces a criterion fitted to the model it was scored on; the number worth publishing is the distance to failure, measured on machines that took no part in the fit.

Such a capability reaches L2 when the procedure is reproducible and its refusals are reachable, and that is the whole of what "a procedure" buys. L3 still needs the same two things every other row needs -- item-by-item sensitivity and an independent cross-check, e.g. the same procedure replayed on a second plant -- so a procedure is not a shortcut past the evidence levels, and it never reaches L4 without hardware.

The three obligations are executable rather than aspirational. test_sop_outer_loop.cpp drives the outer-loop procedure end to end -- identify, propose, measure, held-out acceptance -- on two machines of different inertia, and records the objective as a distance to failure (tolerance - |j_identified/j_nameplate - 1|), a number that changes sign exactly where the library refuses. A gain fitted on the wrong machine is caught in both directions by a band whose two edges are themselves measured (the gain law's own residual, and the smallest nameplate error the repo calls actionable). The three red proofs were run and are recorded with the numbers: replacing the held-out machine with a copy of the fitted one, deleting the refusal path, and collapsing the parameter search to a single setting each turn exactly the expected case red. With that, the replay-on-a-second-machine half of L3 is in place for this procedure; the sensitivity half is not, so the row stays L2.

core/brake_chopper.hpp

SilBrakeChopper.TheChopperHoldsTheBusAndTheBooksClose

core/min_pulse.hpp

MinPulseOutput carries duty (what to command), lost_vs (the volt-seconds the bridge will not deliver, signed and per phase) and narrowed; the residue is readable through carry(), which is what lets a trace tell "the loop is asking for something the driver refuses" from "the loop is fine".

SilMinPulse.ThePlantTransmitsWhatTheDriverAllowsAndThePolicyKnowsThePrice

core/single_shunt.hpp

ShuntVerdict has three answers, not a boolean: Measurable, WindowTooNarrow (this period cannot be read, the reference is near a sector boundary) and NoActiveVector (nothing flows through the shunt at all, so nothing is missed), plus ShuntWindow.window_s / needed_s, which say how far from the edge the period was. A refused reconstruction returns valid == false and zeros, so a caller that checks only the numbers sees a motor drawing no current -- which is why the flag exists.

Param for a configuration that can never read anything (2*(t_settle+t_sample) >= T), for a non-finite timing and for a duty outside [0, 1]; a period outside the window is not a Param -- it is Ok with valid == false, because a narrow window is the normal operating condition and not a configuration error.

SingleShunt.TheBlindSpotIsLowModulationNotTheVoltageLimit

na -- stateless, one period at a time, and the thing it holds is a verdict rather than an accumulated value.

core/mtpv.hpp

MtpvPoint names which ceiling decided the point: voltage_limited is true only when the voltage ellipse moved the answer, and current_a is the margin to the current ceiling, so a host can tell "the voltage is what limits me" from "the current is". base_speed_rad_s() is derived (v_max over the flux magnitude at the current-limited point), not v_max/psi_f -- on the in-domain profile the two differ by 4x, 725 against 2520 rad/s. The boundary case is the band where both ceilings are active at once (725 to 1191 rad/s there): a single-constraint law reports that band as 30 % over the voltage ceiling, which is what the case asserts.

Param for a ceiling that is not positive, a non-positive inductance, a negative flux linkage, zero pole pairs and anything non-finite, and Param from at_speed() for a speed that is not finite. There is no "no answer" case above zero speed: the i_q = 0 point on the ellipse is always inside the current circle, so the candidate set is never empty and a zero-torque point is returned rather than a failure.

Mtpv.StayingOnTheCurrentLimitThereWouldOvervoltTheDrive

na -- stateless, one speed at a time, and what it produces is an operating point rather than an accumulated value.

core/cogging_comp.hpp

CoggingCompOutput separates the two ways a compensator can stop working: gain is the frequency fade ("we chose not to ask for this ripple") and clipped is the current ceiling ("we asked and it was refused"), with torque_nm carrying the cancelled torque before either limit. A compensator that reports only its output current cannot be told apart from one that is silently doing nothing.

Param for a machine that cannot produce torque at the id it is given (dT/diq = 0 at the flux-nulling current, where no current can cancel a torque), for any non-finite input, and for a fade band that is inverted or non-finite. A table of nothing is Ok with a zero offset -- there is no table, so there is no decision to report.

CoggingComp.ATableWithTheWrongPhaseCancelsNothingAtAll

na -- stateless, one period at a time, and what it produces is an offset rather than an accumulated value.

core/cogging_learn.hpp

CoggingLearnReport reports revolutions and the speed band on every exit, including the refused ones: a refusal that says nothing leaves the caller guessing whether to spin longer, slower, or steadier, and those are three different actions. A table it never saw is absent from the output rather than extrapolated, because a compensator acting on an invented harmonic injects a ripple of its own. Reachable from C (six experimental entries: foc_cogging_learn_create/accumulate/ready/finish/reset/destroy), so a script can learn a machine's table. What this answer is, is a table, so the C contract carries a capacity clause the C++ one does not need: finish() echoes required (how many entries the answer needs) and capacity (how many the caller offered) on every return, and given too few slots it refuses with FOC_ERR_PARAM instead of writing a shorter table -- a truncated table tells the caller it asked for fewer orders, and the harmonics it is missing are exactly the ones nobody kept a record of. Passing out_table == NULL asks for the report alone: FOC_OK with count == 0 then means the window is a measurement and there was nowhere to put it, which the C++ signature cannot say, because there nullptr with capacity == 0 is just another refusal. A short buffer is the caller's defect and answers FOC_ERR_PARAM; the window's own refusals stay FOC_ERR_STATE, and both are reported: the buffer verdict wins the return code because it is the one the caller can fix without changing the physics, and result.status still names the window's verdict underneath.

State for fewer revolutions than configured, |omega| outside [min, max] either side, a window whose speed spread exceeds speed_tolerance, a saturated sample anywhere in it, and a destination with no room for the table; Param for order 0 (a constant torque is a load, not cogging), an inverted or non-finite band, a non-finite tolerance, and unusable machine parameters. Nothing was written in any of those cases.

CoggingLearn.TheLearnedTableCancelsTheInjectionItWasLearnedFrom

na -- the accumulators are sums over a finite window that is thrown away on reset(), and what leaves the class is a table rather than a per-tick output.

core/thermal_limit.hpp

ThermalBudget separates "this current can be held forever" from "this current can be held for five more seconds" instead of reporting one number for both: crosses == false with seconds infinite is the sustainable answer, and collapsing the two is how a scheduler throttles a machine that was never in trouble. ThermalLimitReport reports settle_at_cont_c so the assumption behind the continuous current is visible rather than implied.

Param for rt <= 0 (no cooling path), rs <= 0 (no copper to heat), a negative alpha (a winding that cools as it heats is not a model), and a reserve that is not above ambient (no current can heat the winding down to it). A missing Ct is not an error: the continuous current does not need it, and only the budget then reports that it cannot name a time.

ThermalLimit.TheNaiveLawReadsFifteenPercentHighAndThePlantSaysSo

na -- stateless: every answer is a closed form of the configuration and its arguments, and nothing is accumulated.

core/watchdog.hpp

WatchdogState separates the four answers a feeder can leave behind: Feeding (inside the window), Expired (the window passed), ClockLost (the stamp went backwards) and Unarmed (nothing measured yet). The last two are the point: Unarmed is reported as a State error and never as Ok, because a watchdog nobody feeds protects nothing, and ClockLost is a separate state from Expired because the verdict is the same (stop) and the diagnosis is not. A latched report repeats the numbers that caused the latch instead of growing with the clock.

Param for a zero window (it would trip on every feeder and stop a drive for a reason nobody can act on) and for a kick before any window was accepted -- and a refused window changes nothing, including a latch. State for a poll or kick before the first kick, and for a kick after a latch (it does not re-arm and is not counted as a feed). Fault once expired or clock-lost.

Watchdog.TheDeadlineIsExactForEveryWholeNumberOfControlPeriods

na -- it holds one timestamp and one latch, neither of which is a continuous-output invariant; the latch is pinned by Watchdog.AFeederThatComesBackDoesNotClearTheTrip, which is a sequence rather than a per-tick property.

core/auto_tune.hpp

SpeedTuneResult separates "here are gains measured from this machine" from "I could not measure this machine": valid is the bit, and on a refusal the gains it carries are the nameplate ones, so a caller that applies whatever it gets applies nothing new. reason names which of seven refusals fired, because "spin with a varying current" and "something is pulling on the axis" are different actions. The fit keeps an intercept so a constant unknown load cannot be attributed to the current. Reachable from C (five experimental entries: foc_autotune_create/accumulate/finish/reset/destroy), so a C or Python consumer can run the procedure. A session is its own opaque handle rather than a motor register -- nothing is readable tick by tick, only a window to feed and an answer to ask for -- and finish() answering FOC_OK with valid == 0 is a refusal, not a failure.

Param for a non-positive kt, j_expected, bandwidth or i_max, a negative b_expected, a non-positive tolerance or residual bound, and a window shorter than three samples. State-shaped refusals arrive as valid == false with a reason: too short a window, a saturated period, a current that never varied, a residual above the bound, a negative mechanical pole, and a measured inertia outside the tolerance.

AutoTune.ADoubledInertiaIsRefusedAndTheGainsComeBackUntouched

na -- the window is a finite sum that is thrown away on reset(), and what leaves the class is a Pi config rather than a per-tick output.

motor/drive_supervisor.hpp

SupervisorStatus carries the cause, both masks, the derated limit, the temperature that was used (NaN when no channel answered), the bus voltage, the chopper's duty and the tick number, so "which cause, on which tick, was the output allowed" takes one read.

configure() refuses a band that cannot be a band -- a trip point under its own derating start, a derating end under its start, a bus window the wrong way round, no hard limit, no thermal budget, a chopper that would switch on below where it switches off, no pole pairs -- and leaves nothing stored; step() before configure() answers State and writes no duty, because an unprotected drive is the failure this type exists to prevent.

DriveSupervisor.AnOverCurrentStopsTheOutputOnTheFirstTickItIsVisible

na -- every output is a per-tick decision; the stateful parts (Protector's budget and timers, the chopper's dwell times) are their own types with their own cases.

comm/frame.hpp

FrameStatus names which check failed (start / length / checksum) instead of one generic failure, and SequenceChecker reports missing / duplicate / out_of_order separately. missing counts the frames between the one expected and the one that arrived, so a single skipped frame reports 1.

encode_frame returns 0 and writes nothing when the frame does not fit; decode_frame refuses a short buffer, a late start byte and an over-long length before touching the receiver.

Frame.NoSingleByteCorruptionIsAccepted

na -- the codec holds no state; SequenceChecker holds one byte and one flag, and neither is a continuous-output invariant.

core/bus_current_limit.hpp

BusCurrentLimitOutput carries the authority to apply, whether a bus current arrived at all, and whether the limiter is doing anything -- so "was this command clipped" is answerable without reconstructing the loop.

configure() refuses a ceiling that is not positive, a headroom that does not sit below it, and rates or a gain that are not positive; an unconfigured limiter passes everything through at authority 1 rather than clamping. A step whose period is not positive changes nothing.

BusCurrentLimit.TheCeilingHoldsOnTheBenchAndTheSameBenchExceedsItWithout

na -- the output is a per-tick authority rather than a continuous signal, and the property that matters (scale never exceeds 1, so a limiter cannot become a booster) is asserted in BusCurrentLimit.BelowTheAimNothingHappens.

core/move_trajectory.hpp

TrajectoryPoint carries the position to hand the loop, the speed it is travelling at, and whether anything is still pending -- so "where should the axis be now, and is the move over" takes one read instead of an integrator on the caller's side. That is the whole difference from MotionProfile, which only ever answers "how fast".

Limits that cannot describe motion, and targets that are not numbers, are refused by move_to() and change nothing -- not the target, not the position, not the pending flag. A step whose period is zero, negative or NaN changes nothing either. A trajectory constructed with unusable limits never leaves its start rather than moving with an invented default.

MoveTrajectory.ANewTargetMidCruiseIsANumberTheReferenceCannotJumpTo

na -- its per-tick properties (the velocity changes by no more than a*dt, never exceeds what the remaining distance can still stop from, never passes the target, and is unchanged by a re-aim) are asserted inside MoveTrajectory.ANewTargetMidCruiseIsANumberTheReferenceCannotJumpTo rather than in the algebraic Invariants suite, because they are limits of a sampled law and not identities between transforms.

core/angle_source.hpp

AngleReading carries the quality word, the source that produced the angle, the disagreement the decision was made on (NaN when nothing could be compared) and how long the preferred source has been missing, so "which angle, how far to trust it, and since when" takes one read.

configure() refuses three numbers that cannot describe a band -- a window that is not positive, a degraded bar that is not positive, a blind bar that is not above the degraded one -- and a step before configure() answers Blind rather than using a zeroed-out band. A step whose period is not positive changes nothing.

AngleSource.ALostSourceIsHeldForTheDeclaredWindowAndThenReplaced

na -- the output is a per-tick decision rather than a continuous signal, and the property that matters about it (Blind holds the angle and reports zero speed, so a caller ignoring the quality word still cannot steer with a held constant) is asserted in the case named above.

core/sensor_monitor.hpp

SensorMonitorOutput carries the verdict, which check decided it, the step that was measured, the bound it was measured against, and how many readings have been implausible since the last reset() -- so a log line can say "0.31 rad in one sample against 0.0125 allowed" instead of "bad encoder".

configure() refuses a ceiling that is not positive and a tolerance that is negative or not a number, while a tolerance of zero is accepted: "the ceiling is exact" is a position a caller may take. A period that is not positive leaves every field as it was and answers Unobserved, and so does a first sample -- Unobserved is never Ok, because a monitor nobody has compared anything with must not read as healthy.

SensorMonitor.TheBoundItselfDecidesAndBothDirectionsCount

na -- a decision about one reading rather than a continuous signal; the property that matters about it (a verdict is about a reading and not a latch, so the next good sample is Ok again while the count keeps the history) is asserted in the two cases named above.

core/thermistor.hpp

NtcDivider::temperature_c answers false at both rails and leaves the receiver untouched, because 0 and full scale are what an open and a shorted thermistor produce and both are ordinary numbers on the curve; valid_config() reports a divider that cannot exist before the first reading is attempted.

valid_config() is asked at construction by whoever builds the converter, and every conversion re-checks it, so a typo in series_ohm cannot silently produce a temperature.

Temperature.TheInverseUndoesTheForwardModelAcrossTheWorkingBand

na -- a conversion is a pure function of one code and its configuration.

core/commissioning_flow.hpp

completed_mask() and failed_stage() are the two words a support call needs: how far the session got, and which stage gave up. state() separates Running from Idle on purpose -- a session interrupted by a reset has one stage that started and never reported, and "not started" is a different answer.

A plan that is empty, longer than the enumeration, names a stage twice, or names one that does not exist is refused with Param at begin() rather than repaired; complete() and fail() refuse a stage that is not the one in progress, so a late report from an abandoned stage cannot move the session.

CommissioningFlow.AFailureKeepsWhatWasAlreadyObtainedAndNamesTheStageThatGaveUp

na -- it holds a session record, not a signal; the properties that matter (the mask survives a failure, and nothing starts after one until reset()) are asserted in the case named above.

comm/board_record.hpp

decode_board_record() answers with the offset it stopped at, and the four structural refusals are separate words rather than one "invalid": a wrong marker sends a reader to the writer, a failed check value to the transport, and a BadField offset to the check that produced an impossible row.

encode_board_record() refuses a short buffer or an unusable record before the first byte, so a truncated record never reaches flash; the padding past count must be zero on the way in and is verified on the way out; a negative zero is not a padding zero, because it compares equal to 0.0F and encodes differently.

BoardRecord.APaddingRowThatSpeaksOrACountThatCannotBeIsRefused

na -- a codec holds no state and produces no signal; the property that matters (no single-byte corruption of the blob reads back as a record) is asserted in BoardRecord.NoSingleByteCorruptionIsAccepted.

comm/commissioned_set.hpp

SetStatus names the check that failed (short / marker / schema / reserved / check value / field) and SetError.offset names the byte, so a reader learns which number to re-measure rather than which byte to stare at.

encode_commissioned_set returns 0 and writes nothing for a short buffer or an unusable set; decode_commissioned_set refuses a short buffer, a foreign marker, an unread schema, a non-zero reserved byte and a failed check value before touching the receiver, and leaves it untouched on every refusal.

CommissionedSet.EverySingleByteChangeIsRefused

na -- a codec is a pure function of its buffer; the only state is the receiver, which is written once on success.

comm/encoder_stream.hpp

EncoderFrame separates "this frame arrived and is not trustworthy" (State plus crc_ok == false, with the counts still filled in so a log has something to show) from "this buffer cannot be read at all" (Param, with no value handed back). TurnAssembler::Step separates a wrap from a gap: jumped == true means the travel was unknowable, and then unwrapped does not move.

Param for a null buffer, a stream whose length is not frame_bits(), a layout with 0 single-turn bits, more than 31 single-turn bits, more than 32 data bits, or negative multi-turn bits; and for an assembler whose single-turn bits are outside 1..31 or whose declared maximum step is 0 or above half a turn (above which the wrap question is undecidable). State for a CRC mismatch, a failed-CRC frame fed to the assembler, or a gap.

na -- the decoder is a pure function of one frame, and the assembler holds one previous count and one origin, neither of which is a continuous-output invariant.

a NULL receiver, an id with no row, and any register whose C function refuses all return false with the word untouched -- except the two count registers, whose C functions document NULL as 0.

sector, changed, holding and skipped, plus rejected()/illegal() counters. holding and skipped are different things and the duty alone cannot tell them apart: one means the pins named no position, the other means they named one the rotor cannot have reached.

analog: in_deadband; ppm: valid; step: pulses, delta_rad and jump. A command source whose only output is a number cannot be told apart from a dead link, and jump is the difference between "the axis moved" and "the axis moved further than one period of motion allows, so a count was lost".

status for the map and limited for every command. The second one is the point: a clipped command and an obeyed one are otherwise identical, and a caller who cannot tell them apart reports a saturating tensioner as holding.

core/stall_start.hpp

"starting", "released" and "cannot start" are three states rather than one number, and Failed is a first-class answer: a load the drive cannot move is a fact about the machine, and a sequence that ramps forever instead of saying so leaves the operator watching a silent axis. Through Motor the same two facts are stall_start_phase() and stall_start_torque_nm(), and they have to be read together: the phase says whether the torque beside it is still the sequence's or the caller's again.

2.3. The four evidence levels

Every quantitative statement on this site carries one of four levels, and the level is part of the statement rather than a footnote: an L2 number is not a weaker L4 number, it is a different kind of claim. The table below is the vocabulary. The worked example for each level is a claim row in the project README.md, and it stays there -- copying one here would give that number a second home with a shelf life, which is the failure this page's matrix exists to prevent.

Level

What it means

How it is checked

What it does not say

L1

Asserted by construction

A compiler flag, a type, or a gate that fails the build

That the behaviour was ever observed at run time

L2

Measured against the model in this repository, with the criterion written before the measurement and the number recorded

A unit test that prints the number and asserts the criterion

Anything about your machine: it is true of the plant in this repository

L3

L2 plus a measured sensitivity -- how far the number moves when the model is wrong in the ways it is known to be wrong

test_sil_sensitivity.cpp, plus a phase-variable cross-check of the model itself

That the model omits nothing that matters to you; it bounds only what is known to be omitted

L4

Measured on physical hardware, with the condition recorded

not available in this repository

--

No page here makes an L4 claim: at the time of writing there is no motor, no inverter and no current probe on this project. A row may state the minimum of the levels its inputs depend on and no more, and where a page quotes a number it names the level it is quoting.

An evidence level answers "how well is this supported". What may be said to a customer about a capability — the sentence, the tier behind it, and the industry it is said in — is What may be claimed, and to whom.
