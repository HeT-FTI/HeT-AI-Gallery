3. Convention alignment

This page is the precondition for comparing anything against an external reference — another FOC implementation, a bench measurement, or an offline model. Angle frames, rotation direction, units and clamping style must agree before any RMSE or overshoot number is computed; otherwise the comparison measures the conventions, not the algorithm.

The conventions below are not a preference: they are whatever include/foc/ already implements. Any reference has to align to them, never the other way round.

3.2. 2. Gains: one word, four meanings

A vendor's kp and ours are not the same object, even when they are the same digits. What the gain multiplies decides its unit, and the unit decides whether the two numbers can be compared at all.

Loop

What the gain multiplies

Unit

In this library

Current

current error

V/A

core::Pi::Config::kp

Speed

speed error

A/(rad/s)

speed_pi_config()

Position

position error, and the output is a velocity command

1/s

PositionP::Config::gain_1_s, position_p_config()

Vendor "position gain"

often torque per radian, commanding torque directly

N·m/rad

not used here: this library puts the speed loop between position and torque

Our position gain closes a first-order position loop through the speed loop. A vendor whose position gain commands torque directly has a different loop, so kp = 20 in their header and 20 1/s here are two different claims about two different plants.

3.3. 3. Scaling names, and what a zero means

The per-call scales are named after the vendor's spelling on purpose, so a ported configuration can be compared field by field:

Field here

Scales

Vendor equivalent

kp_scale

position-loop gain

moteus kp_scale, same meaning

kd_scale

speed-loop proportional gain, i.e. the damping

moteus kd_scale

ilimit_scale

speed-loop integral limit

moteus ilimit_scale

0 in all three means no override, use the configured value, not "zero gain". That is a project-wide rule: zero is only ever a default where zero is not a legal value. The cases are Pi.AZeroIntegralScaleMeansNoOverrideRatherThanAnEmptyWindow, Pi.APerCallGainScaleMultipliesTheProportionalTermWithoutTouchingTheConfig and MotionProfile.TheStiffnessScaleSlowsTheApproachWithoutChangingTheLimits.

3.4. 4. Timing: what the library does not decide for you

Item

What is fixed, and where

Control period

given by the caller (tick(dt_s)); the library never invents a time base of its own

Decimation

by elapsed time (speed_loop_period_s, position_loop_period_s), not by a tick count, so a change of control frequency keeps the physical period

Overrun

Telemetry::max_period_us, and only when the HAL policy exposes a clock. It is an indicator and never a scheduling input

Comparing bandwidths

do not compare a control-loop bandwidth across implementations at different rates without normalising: fielded firmwares run their loops anywhere from tens of hertz to tens of kilohertz, and the same gain means different things at each

3.5. 5. The four traps that actually bite

  1. Mechanical vs electrical angle. A missing pole_pairs makes the whole dq frame rotate at \(1/p\) of the right speed; the symptom is "the current loop never catches up". PlantHal::advance() and PlantPosition must use one conversion, not two.

  2. Amplitude-invariant vs power-invariant Clarke. A power-invariant Clarke (with \(\sqrt{2/3}\)) scales \(|i_{\alpha\beta}|\) by \(\sqrt{3/2}\) — "1 A commanded, 1.22 A delivered". A closed loop hides this: the integrator quietly absorbs the gain error, so only an open-loop comparison exposes it.

  3. Stationary vs rotating zero-order hold. A real inverter pins the voltage vector in the stationary frame for the whole PWM period. Holding it in the dq frame (re-parking every sub-step) adds a spurious zero-order-hold error at speed. Both the C++ plant and the arbiter use the stationary frame.

  4. The ramp trap in steady-state error. On a speed ramp the current loop always lags by \(e = \dot{E}MF / k_i\) (about 1 % here). That is not a defect: before judging "steady-state error", confirm the run is on a constant-speed segment.

3.6. 6. Extra checks before comparing with a third party

Item

What to confirm

dq convention

motor convention or generator convention (\(i_q\) changes sign)

Rotation sense

clockwise or counter-clockwise positive (\(\theta\) changes sign)

Units

per-unit or SI; if per-unit, what are \(V_{base}\), \(I_{base}\), \(\omega_{base}\)

PI anti-windup

present or not, and how: clamping / back-calculation / conditional integration

SVPWM

seven-segment or five-segment; over-modulation or not; per-phase or vector clamping

Sampling and delay

one-period computation delay? mid-point sampling? loop rate versus PWM frequency?

3.7. 7. Status of the SguanFOC reference

  • Not vendored, not built, not in any CI path.

  • Upstream is a single-maintainer project whose licence and long-term maintenance were never audited.

  • Vendoring a snapshot (pinned commit) means putting third-party code into this repository — licence, size and maintenance are all affected, so it is an architecture-level decision that belongs to the repository owner. Until such a decision exists, sections 1 and 3 above are the only valid reference.

  • Even if it were vendored, it would only be read for specific ideas (LADRC, HFI). It produces no comparison data and enters no test. When it disagrees with this page, the default is to distrust SguanFOC.

3.8. 8. Change rule

  1. Any change to a convention above (introducing per-unit, switching to generator convention, adding back-calculation to the PI) must change this page first, then the code, then the L2 reference traces (regenerated with offline_arbiter.py) — and only then may it be committed. Reversing that order yields gates that are green while the convention is wrong.

  2. A new comparison scenario appends a row to the compared quantities table in section 1 and says on that row why it compares what it compares.
