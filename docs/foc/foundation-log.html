1. Foundation corrections

Every claim in this documentation rests on a measurement, and every measurement rests on code that could be wrong. This page is the record of the times it was: what broke, how it surfaced, what it invalidated, and what was re-run afterwards.

It is append-only. A row is never deleted or softened, including the rows that are unflattering -- the proportion of "the library was wrong" to "I was wrong" is information about the library, and erasing it would destroy the only evidence there is.

Why a page rather than discipline: the failure this guards against is not forgetting a bug, it is a wrong number becoming reference data. Once a figure is written into a comparison or a golden trace, every later check endorses it, and the error stops looking like an error. An entry here is what lets a reader ask "was this measured before or after that was fixed".

1.1. Three kinds, and they are deliberately not merged

Kind

What it means and what it costs

code

The library was wrong: a computation, a contract, a constant that does not exist. These earn unbounded effort, because a wrong foundation multiplies -- every capability built on it inherits the error and the evidence for it.

criterion

The criterion was wrong: it did not bind to the physics it claimed to test, or the tolerance was chosen after seeing the number. Fixing this is re-deriving the tolerance and writing down where it came from, which is slower than widening it.

reading

The analysis was wrong: the measurement was fine and the reading was not. The fix is to the method, never to the code -- patching code because a reading was misread damages a foundation that had nothing wrong with it.

The distinction is the whole point. Treat a reading as a code and the library collects defensive patches it does not need; treat a code as a reading and a real defect is recorded as a personal slip and left in place.

1.2. Where an entry sits

Two chains, because a defect is answered by one of two different groups of people. The signal chain is the machine and the arithmetic that describes it: which part of the drive was being computed. The engineering chain is what the library is made of and how it is checked: which part of shipping or verifying it was being done. A signal-chain entry is somebody's to re-derive; an engineering-chain entry is somebody's to re-run.

An entry is placed by the module it names, not by the kind of mistake, because that is how a reader arrives: from the capability whose number moved. When an entry names no module, the subject of its first sentence decides. Nothing is ordered by date inside a section -- the commit is on the entry, and the page is a body of knowledge rather than a timeline.

1.3. How the blast-radius column is produced

Not by memory, and not by reading the diff and guessing. The command is

python3 .github/project/gates.py claims --impact <path or identifier>

which reads the basis graph in .github/project/claim-basis.json and prints every claim that rests on that thing, together with the cases to re-run. evidence in the README answers "what checks this claim"; basis answers "what would invalidate it", and the two are different -- a claim can have evidence that passes while resting on a plant model that is wrong, which is the failure shape exactly.

Twelve of the forty-one claim rows had a basis when the graph was first built; the other twenty-nine were listed explicitly as unmapped and the gate printed that count on every run. It is now complete -- 51 of 51 installed headers are mapped -- and the count is still printed, because the mechanism that filled it is the same one that has to keep it full: a row in neither list fails the build, and a new header arrives with either a basis or a stated reason it has none.

The graph is generated from the code rather than from recollection. An edge is either a compile edge (a foc/ header the module or its own .cpp includes directly) or a semantic one (another module whose value the claim quotes without including it -- core/pi.hpp's claim quotes numbers that motor/motor_config.hpp computes, and if that formula moves the claim is stale while every test still passes). Six headers are roots with no incoming edge and carry a self-edge; the asymmetry is stated rather than smoothed over.

The graph is also checked for rot: a basis entry naming a file that no longer exists, or an identifier that appears nowhere in include/ or src/, fails the build, because a decayed graph returns a confident and wrong blast radius and that is worse than returning nothing. It caught two while being filled -- src/core/protection.hpp, which is a header, and three entries that resolved to nothing.

One answer worth knowing before the next change: 156 of the 169 claims rest on `core/types.hpp`. That is not a surprise, and it is the reason a change to the value layer is not a small change no matter how mechanical it looks.

The probe that first measured the code in the control path ran with pwm_freq_hz = 0 in the setup, which drives the carrier phase increment to zero on its own

Kind reading. The 0.00000 it reported was therefore guaranteed before the defect was consulted -- and the same rig, after the fix, still read 0.00000 at 6 kHz and would have looked like a failed fix.

Surfaced Sweeping the carrier rate against an explicit pwm_freq_hz: the same code, one knob changed, went from 0.00000 at 1/2/4/5 kHz to 0.60/0.65/0.66/0.67. A probe is only worth its reading once it has been shown able to produce a non-zero one.

Blast radius The the code in the control path verdict, re-measured. Pre-fix 0.00000 at all four rates with observer = HFI; post-fix 0.45-0.67 across eight rate/PWM combinations. Same window, one knob, both directions.

The same plant integrated a fixed 50 us (DT) per write_duty call, while golden.py ticks at 100 us

Kind code. The model advanced half a period per call, so simulated time ran at half speed -- an exact factor of two on top of the code in the control path's seven.

Surfaced Reading the constant after the code in the control path's factor of seven did not explain the whole 14x: 250/7 = 35.7, and the measurement said 17.8. grep DT found 50e-6 against the caller's 1e-4.

Blast radius The plant now takes dt_s, golden.py carries one DT_S that both the loop and the plant use, and the two development scripts that already ticked at 50 us are unaffected. Together the code in the control path and the code in the power stage account for 14.05x, and the corrected measurement is 243.57 rad/s against 250 (-2.57 %).

The graded protection ladder had a case for the derating curve (derated_limit(T), a pure function) and a case for the trip, and nothing in between: no case ever stepped the protector with a temperature inside the band, and no case anywhere asserted active_mask, so the enum-order ranking the header documents was unexercised too

Kind criterion.

Surfaced Writing the two cases the plan's own criterion named -- "each rung has a case, and an implementation that trips without derating must be red" -- and then building exactly that wrong implementation: replacing t_trip_c with t_derate_start_c in the over-temperature condition left seven of eight protection cases green. Only the new ladder case failed.

Blast radius Two cases, and the todo in the capability matrix's boundary column that had been standing in for them is now a case name. The rule this row is about: a capability with a curve test and a trip test can still have no test of the thing it is for.

FaultCode::Stall was in the same state LostSync had been in (the code in the control path): defined, ranked, named in the C API, and never raised

Kind code. The load-step sweep proved what that costs -- at four times the rated torque the machine was pushed backwards to -895 rad/s while the loop held a +400 rad/s command and reported nothing at all.

Surfaced The load-step test was written for gap 3 of the C2 plan and its own falsifier produced this: a band that is only ever observed passing cannot show that the over-range case is unhandled. 20 of 20 within +-50 % were held, so nothing in the sweep pointed at the hole; one run beyond it did.

Blast radius The detector is narrow on purpose: full current (90 % of the ceiling), and the machine not moving the way it was told (reversed, or below a quarter of the command), and sustained for 100 ms. Any one of the three alone fires on a large speed step, on a light load, or on the step's own transient -- and a protection that trips wrongly gets disabled. Measured after: the 4x case faults with stall in 100 ms; the 20 in-range cases still pass untouched.

The i2t_cooling_s > 0 guard had never been taken

Kind code. The mutant makes it >=, which turns dt / 0 into inf and empties the thermal budget every step; nothing noticed, because every configuration in the suite supplies a positive thermal constant, so the branch that exists for the zero case was never executed. A zero cooling constant is a legitimate configuration ("no cooling"), and with it the budget is exactly i^2*t: 3 A for 32 steps of 1/64 s is 4.5 A^2*s, the budget itself, and the thirty-third step is the first that spends past it.

Surfaced

Blast radius

reset() and reset_cold() are public operator actions and had no test that called them

Kind code. The class comment promises three things -- "clear the latched faults, an operator action, never automatic", "I2t is not cleared here: the winding is still hot", and reset_cold() is the one that forgets the heat -- and not one of the three had a witness. Line coverage was satisfied because bridge.cpp reaches reset_cold() from the C ABI, which is exactly the kind of green that means nothing: the module's own tests never walked the two loops.

Surfaced Sanitisers found it, and the measurement that matters is that one was not enough. A one-line probe (a struct with bool a[8], then a[8] = false) reports nothing under AddressSanitizer and one finding under UndefinedBehaviorSanitizer, because ASan's redzone surrounds an object and not the members inside it: flags[8] in step() is a standalone local and dies under ASan, while tripped_[8] is a member and only dies under UBSan's array-bounds. The harness now builds with -fsanitize=address,undefined -fno-sanitize-recover=all -- the last flag because UBSan otherwise prints a line and still exits 0, which the harness would have recorded as a survivor. Two of the six surviving overruns then turned out to be equivalent rather than invisible, and only the instrument could tell: reset()'s write is guarded by fault_is_latched(code), which is false for the out-of-range code in the ninth iteration, so the overrun never executes. Recording them as "needs a memory checker" would have been a wrong label kept forever; being able to say "equivalent, measured" required the tool that can see the writes that do happen. protection closed at 77.6 % (52/67) with 15 survivors, all classified, none of them invisible.

Blast radius The general lesson is about coverage rather than about this block: a function reached only from another layer's tests is a function whose own contract is untested, and no percentage will say so.

The sufficiency question for the geometric layer was answered by fetching rather than by recalling, and the answer splits in two

Kind reading. Geometry is not the problem: pip download pyleecan yields a 9.2 MB pure-Python wheel whose Data/Machine/ directory ships complete 2D geometries for named machines -- TESLA_S, AUDI_eTron, IPMSM_A, SPMSM_001..015, SynRM_001, SCIM_001/006. IPMSM_A alone carries 48 slots, 4 pole pairs, 83.82 mm of stack, stator radii 55.32/80.20 mm, rotor radii 80.95/134.62 mm and the full slot and magnet-hole dimensions, which is everything a 2D magnetostatic solve needs.

Surfaced Reference values are the problem, and the same wheel is why. This version of pyleecan ships only MagFEMM/FluxLinkFEMM, and even the equivalent-circuit path (EEC_PMSM.comp_parameters()) reaches for comp_fluxlinkage() on top of FEMM. There is no FEMM binary here and no wine, so an authoritative geometry can be borrowed but no authoritative number comes with it. That changes what the third layer can honestly be. Not "borrow a geometry, read off Ld/Lq, compare" -- that would be comparing against a value we produced ourselves and calling it external. Instead: write the 2D magnetostatic solver (scikit-fem 12.0.2 is a pure-Python wheel, installable without sudo), first validate the solver on a case whose answer is closed-form and derived independently of this repository's model, and then put the validated solver on an authoritative geometry to measure what the lumped model's assumptions -- sinusoidal air-gap flux, no slotting ripple, no cross-saturation -- are actually worth. The output is an error term for the L3 rows' budgets, which is the one thing a geometric model can supply and no algebraic re-derivation can.

Blast radius The MCU question is separate and worth separating: anchoring on a specific part (STM32G4 was the earlier proposal) supplies no magnetics at all, because the MCU never enters the magnetic model. What it does supply is numbers for the timing and quantisation error sources the budget table currently assumes -- PWM duty resolution from the high-resolution timer, ADC LSB and sample jitter, dead-time granularity -- so it is a real gain for the hardware-adjacent rows and no gain at all for this one.

The thermal budget accumulated `i^2 / dt` instead of `i^2 * dt`, and that line existed only in the working tree. q is an energy in A^2*s, so the increment over one period is i^2 * dt; dividing by dt made a machine running at its own nameplate spend 180000 A^2*s per 50 us period against a 4.5 A^2*s budget, i.e. the protection tripped I2t on the first healthy control period

Kind code. This is one character and it accounted for 14 of the 15 failing cases in the code in the gate layer: the 13 Protection.* cases and the three c_api_validation failures, which assert FOC_FAULT_NONE and output_allowed on a healthy step.

Surfaced Surfaced by running the suite, not by reading the line. The injection matrix printed the diagnosis in one screen: injected None -> I2t WRONG (a healthy input producing a fault) and injected Stall -> I2t WRONG (a different mechanism's code winning the ranking because I2t also tripped). That second row is the instructive one -- the observable symptom was two wrong cells out of eight, but only one mechanism was broken, and the ranking hid it. A chain of else if checks would have shown "Stall does not work"; the independent-flag matrix showed "I2t fires when nothing is wrong", which is the actual defect.

Blast radius The criterion already existed and was never executed against. The test's own comment states the equilibrium of this model is i_cont^2 * tau = 3^2 * 0.5 = 4.5 A^2*s, and that budget is what the config sets. Only i^2 * dt reproduces that identity; the dimensional check is one line. So this row is not a missing test but an unrun one, and the blast radius in a real product is exactly the worst one available: a protection that trips on its rated current protects nothing and stops the machine. `HEAD` already had `i^2 * dt`. The division was uncommitted, so the repair was a revert of a regression that no commit ever contained -- and the diff says so unambiguously: after the repair the corrected line shows up as context, not as a change, and the only thing the file actually gained was the paragraph of comment above it. The lesson is not "someone made a typo" but that a working tree can be red while `main` is green, and nothing in this repository noticed for as long as nobody ran it -- which is what the code in the gate layer is about. The comment now pins the units and the i^2 * tau identity so the next edit in that direction has to argue with the paragraph first. Suite re-run after it: the reading in the build.

The first rig that measured the dead band was scaled so that a 20 mrad step demanded 1 N*m against a 3 A current limit: the loop saturated on the first period and limit-cycled at 125 mrad, and the file measured that instead of the friction

Kind reading. The module was never wrong; the instrument was.

Surfaced The trajectory print rather than the summary: theta swinging between -26 and +125 mrad while the demanded torque sat on the clamp for most of every cycle. Kind reading. It does not: the latch turns around as soon as the demand passes the term, so there is no such equilibrium -- with the reference held at zero the axis simply walks away, and the size of the walk is set by where the loop's own demand finally balances the compensation.

Surfaced Measuring it instead of deriving it: 114 mrad of excursion in the first attempt and 5.625 mrad of net travel in the second, against a predicted 2 mrad in the wrong direction.

The first criterion for "the residual drops" was a single step's final position

It is not reproducible: where inside the dead band the trajectory happens to stop depends on the step size and the ringing, and the same three mechanisms read 2.9, 1.1 and 0.24 mrad at 20, 20 and 200 mrad steps -- a criterion that would have been "fixed" by choosing the step that made it look right.
