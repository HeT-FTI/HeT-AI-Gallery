1.1.4. Torque below base speed

The task: from a torque request, produce a dq current reference this machine can actually deliver, and drive both current axes to it inside the voltage the modulator has. This is the page every other page stands on -- the field weakening page, Above base speed, answers the same question above base speed, and the observer on the startup page, Bringing a sensorless machine up, exists so that the angle this page assumes is available without a sensor.

1.1.4.1. What you need

  • foc/core/reference.hpp -- the reference policy. MtpaReference for a salient machine; the default d = 0 generator for a surface one.

  • foc/core/pi.hpp -- one controller per axis. Two instances, not one shared: the integral state is per axis.

  • foc/core/feedforward.hpp -- the axis cross-coupling and back-EMF terms, added after the PI so the PI keeps its own-axis job.

  • foc/core/limits.hpp -- clamp.

  • foc/motor/motor_config.hpp -- the two gain laws and the per-axis output clamp, derived from the nameplate by current_pi_config(). The ceiling the modulator cares about is a different object: it is the pair's inscribed circle, and High speed and modulation covers why it is not the rail.

1.1.4.2. A minimal program

docs/doxygen/dox/demos/torque-reference.cxx is the whole of it, compiled with the flags this repository's strict gate uses. It names one salient machine once and asks two reference policies the same q command:

  1// Torque -- torque below base speed: the reference policy, the two PIs, the
  2// feedforward, and where the voltage ceiling belongs. No hardware, no plant:
  3// the point of the example is the wiring a board shares with the SIL bench.
  4//
  5// Build it the way the `demo` gate does -- the example calls into the library, so the
  6// sources are part of the command, and `-Iinclude` alone fails at the link. A renamed
  7// source turns that gate red instead of leaving a stale instruction here:
  8//   g++ -std=c++17 -fno-exceptions -fno-rtti -Wall -Wextra -Werror -Iinclude
  9//   docs/doxygen/dox/demos/torque-reference.cxx src/core/*.cpp
 10//   src/core/observer/*.cpp src/motor/*.cpp src/driver/*.cpp src/api/foc_api.c
 11//   src/api/bridge.cpp src/version.c
 12//   -o /tmp/torque-reference
 13//
 14// 转矩 —— 基速以下转矩：参考策略、两个 PI、前馈，以及电压天花板该放在哪。
 15// 不需要硬件也不需要被控对象：这个例子要展示的是"板子与 SIL
 16// 台架共用的那段接线"。
 17
 18#include <cmath>
 19#include <cstdint>
 20#include <cstdio>
 21
 22#include <foc/core/feedforward.hpp>
 23#include <foc/core/limits.hpp>
 24#include <foc/core/pi.hpp>
 25#include <foc/core/reference.hpp>
 26#include <foc/core/types.hpp>
 27#include <foc/motor/motor_config.hpp>

 29namespace {
 30
 31constexpr float kTwoPi = 6.28318530718F;
 32
 33// One salient machine, named once. `lq = 2 * ld` is the shape MTPA exists for:
 34// on a surface machine the d axis earns nothing and the two policies coincide.
 35// 一台凸极机，只在这里写一次。`lq = 2 * ld` 正是 MTPA 存在的形状：表贴机上 d 轴
 36// 没有额外收益，两种策略给出同一个答案。
 37constexpr float kLd = 4.0e-4F;
 38constexpr float kLq = 8.0e-4F;
 39constexpr float kPsiF = 0.01F;
 40constexpr float kIMaxA = 3.0F;
 41
 42constexpr float kRs = 0.5F;
 43constexpr float kVBusV = 24.0F;
 44constexpr float kDtS = 5.0e-5F; // 20 kHz current loop
 45
 46// The nameplate, once. Six of these fields never reach the current loop -- they
 47// are here because `current_pi_config()` takes the configuration a caller already
 48// has, instead of the two numbers it happens to read.
 49// 铭牌，只写一次。其中六个字段根本进不到电流环——它们在这里是因为
 50// `current_pi_config()` 要的是调用方本来就有的那份配置，而不是它恰好读的那两个数。
 51constexpr foc::motor::MotorConfig kMachine{
 52    kRs, kLd, kLq, 0.08F, 1.0e-4F, 1.0e-4F, std::uint8_t{4}, kIMaxA, 20.0e3F,
 53    200.0F};
 54
 55// A current loop closed at 1 kHz. The gains come from the library's own rule
 56// (`kp = 2*wb*Ld - Rs`, `ki = wb^2*Ld`), not retyped here: the equation table
 57// in the documentation carries that rule with a pointer to this function, and a
 58// second copy in an example is a second law that can drift from it.
 59// 1 kHz 闭环的电流环。增益来自库自己的规则（`kp = 2*wb*Ld - Rs`、`ki = wb^2*Ld`），
 60// 不在这里重抄：文档里的方程表带着指向这个函数的指针，而示例里的第二份就是一条
 61// 会与它走散的第二定律。
 62constexpr float kLoopOmega = kTwoPi * 1000.0F;
 63
 64// The ceiling is a **vector** ceiling: `v_bus/sqrt(3)`, the inscribed circle of
 65// the hexagon, which is where `svpwm.hpp` reports `saturated`. It is not
 66// `v_bus/2` -- that is the per-axis clamp inside `Pi::Config`, a different
 67// object, and a pair of axes both sitting on it asks for `0.707*v_bus`, which
 68// the bridge cannot deliver linearly.
 69// 天花板是**矢量**天花板：`v_bus/sqrt(3)`，六边形的内切圆，也就是 `svpwm.hpp`
 70// 报 `saturated` 的位置。不是 `v_bus/2`——那是 `Pi::Config` 里的每轴钳位，是两个
 71// 不同的对象；两轴同时贴着它，合成矢量就是 `0.707*v_bus`，桥臂无法线性交付。
 72constexpr float kVCeilingV = kVBusV / 1.7320508F;
 73
 74/// One current-loop tick on one axis: PI plus that axis's feedforward term, with
 75/// no ceiling applied here -- the ceiling belongs to the pair, see
 76/// `limit_vector()`.
 77/// 一个电流环周期上的单轴：PI 加该轴的前馈项，**不**在这里钳位——天花板属于那对
 78/// 数，见 `limit_vector()`。
 79auto tick(foc::core::Pi &pi, float reference, float measured, float ff) noexcept
 80    -> float {
 81  return pi.step(reference, measured, kDtS) + ff;
 82}
 83
 84/// Limit the **pair**, not each axis. Clamping them separately keeps each inside
 85/// its own bound and still lets the vector out; scaling both keeps the angle the
 86/// loop asked for, which is the one thing the modulator cannot restore.
 87/// 限的是**那对数**，不是每个轴。分开钳位只能保证各自不越界，合成矢量仍然会出去；
 88/// 两边同比例缩，才不会改变环路要的角度——而角度是调制器无法恢复的东西。
 89auto limit_vector(foc::core::Dq<float> v, float ceiling) noexcept
 90    -> foc::core::Dq<float> {
 91  const float magnitude = std::sqrt((v.d * v.d) + (v.q * v.q));
 92  // `ceiling` is a positive constant, so a zero vector takes the early return and
 93  // the division below never divides by zero.
 94  if (magnitude <= ceiling) {
 95    return v;
 96  }
 97  const float scale = ceiling / magnitude;
 98  return foc::core::Dq<float>{v.d * scale, v.q * scale};
 99}

101} // namespace

103auto main() -> int {
104  // Two instances of the same policy, and the difference between them is the
105  // whole point of this example: `i_d_per_speed_a_s_per_rad` defaults to 0,
106  // which *refuses* d-axis current outright, because a d-axis current is only
107  // safe if somebody has said how the angle is measured. Left at 0, MTPA
108  // answers exactly what the d=0 policy answers.
109  // 同一个策略的两个实例，它们的差别就是本片的要点：`i_d_per_speed_a_s_per_rad`
110  // 默认是 0，即**完全不施加** d 轴电流——因为只有在"角度怎么测"有交代之后，
111  // d 轴电流才是安全的。留在 0，MTPA 给出的答案与 d=0 策略完全相同。
112  const foc::core::MtpaReference::Config shipped{kLd, kLq, kPsiF, kIMaxA};
113  // A large allowance is safe only for a machine whose angle is measured (a
114  // position sensor): the rate exists to bound how much a *wrong* angle can
115  // cost, so with a sensor the bound is not needed.
116  // 大的许可值只对"角度是被测出来的"机器才是安全的（带位置传感器）：这个比率
117  // 存在是为了限制**错的**角度能造成多大代价，有传感器时那道界不需要。
118  const foc::core::MtpaReference::Config with_allowance{kLd, kLq, kPsiF, kIMaxA,
119                                                        1.0F};
120  foc::core::MtpaReference mtpa_shipped(shipped);
121  foc::core::MtpaReference mtpa(with_allowance);
122  foc::core::NullReferenceGenerator d_zero{};
123
124  // One law, one place. `current_pi_config()` returns the gains *and* the
125  // per-axis output clamp, which is why nothing here recomputes either.
126  // 一条定律，一个位置。`current_pi_config()` 同时返回增益与**每轴**输出钳位，
127  // 所以这里两边都不重算。
128  const foc::core::Pi::Config gains =
129      foc::current_pi_config(kMachine, kLoopOmega, kVBusV);
130  foc::core::Pi pi_d(gains);
131  foc::core::Pi pi_q(gains);
132  foc::core::DecouplingFeedforward feedforward(
133      foc::core::DecouplingFeedforward::Config{
134          kLd, kLq, kPsiF,
135          foc::core::DecouplingFeedforward::Terms::CrossAndBemf});
136
137  // A standstill measurement: the loop is asked to move the current away from
138  // zero, which is the case where the integral term does all the work.
139  // 静止时的实测值：让环路把电流从零推出去，这正是积分项承担全部工作的情况。
140  const foc::core::Dq<float> measured{0.0F, 0.0F};
141  const float omega_e = 20.0F;
142
143  std::printf("%7s | %12s %8s | %12s %8s | %8s %8s\n", "iq cmd", "mtpa(0) id",
144              "iq", "mtpa(allow) id", "iq", "d=0 id", "iq");
145  for (float iq_command = 0.5F; iq_command <= kIMaxA + 0.01F;
146       iq_command += 0.5F) {
147    const foc::core::ReferenceInput in{iq_command, omega_e, kVBusV, measured};
148    const foc::core::Dq<float> as_shipped = mtpa_shipped.generate(in);
149    const foc::core::Dq<float> allowed = mtpa.generate(in);
150    const foc::core::Dq<float> with_d_zero = d_zero.generate(in);
151    std::printf(
152        "%7.2f | %12.4f %8.4f | %12.4f %8.4f | %8.4f %8.4f\n",
153        static_cast<double>(iq_command), static_cast<double>(as_shipped.d),
154        static_cast<double>(as_shipped.q), static_cast<double>(allowed.d),
155        static_cast<double>(allowed.q), static_cast<double>(with_d_zero.d),
156        static_cast<double>(with_d_zero.q));
157  }
158
159  // One tick at the top of the sweep, to show the voltage the two axes ask for
160  // and that the ceiling is applied after the feedforward, not inside the PI.
161  // 走到扫描顶端的那一拍，用来展示两轴要的电压，以及天花板夹在前馈**之后**、
162  // 不是夹在 PI 内部。
163  const foc::core::ReferenceInput top{kIMaxA, omega_e, kVBusV, measured};
164  const foc::core::Dq<float> i_ref = mtpa.generate(top);
165  const foc::core::Dq<float> v_ff =
166      feedforward.generate(foc::core::FeedforwardInput{omega_e, measured});
167  const float v_d_raw = tick(pi_d, i_ref.d, measured.d, v_ff.d);
168  const float v_q_raw = tick(pi_q, i_ref.q, measured.q, v_ff.q);
169  const foc::core::Dq<float> v =
170      limit_vector(foc::core::Dq<float>{v_d_raw, v_q_raw}, kVCeilingV);
171  std::printf(
172      "\none tick at iq = %.2f A, omega_e = %.1f rad/s, v_bus = %.1f V\n",
173      static_cast<double>(top.iq_command_a), static_cast<double>(omega_e),
174      static_cast<double>(kVBusV));
175  std::printf("  reference   id = %+8.4f A  iq = %+8.4f A\n",
176              static_cast<double>(i_ref.d), static_cast<double>(i_ref.q));
177  std::printf("  feedforward vd = %+8.4f V  vq = %+8.4f V\n",
178              static_cast<double>(v_ff.d), static_cast<double>(v_ff.q));
179  std::printf(
180      "  asked       vd = %+8.4f V  vq = %+8.4f V  (|v| = %.4f V)\n",
181      static_cast<double>(v_d_raw), static_cast<double>(v_q_raw),
182      static_cast<double>(std::sqrt((v_d_raw * v_d_raw) + (v_q_raw * v_q_raw))));
183  std::printf(
184      "  commanded   vd = %+8.4f V  vq = %+8.4f V  (|v| = %.4f V, ceiling "
185      "%.4f V)\n",
186      static_cast<double>(v.d), static_cast<double>(v.q),
187      static_cast<double>(std::sqrt((v.d * v.d) + (v.q * v.q))),
188      static_cast<double>(kVCeilingV));
189  std::printf("  status      d = %d  q = %d  (0 = Ok)\n",
190              static_cast<int>(pi_d.status()), static_cast<int>(pi_q.status()));
191
192  // The limiter, shown on the pair that needs it. Two axes each sitting on the
193  // per-axis clamp `current_pi_config()` puts in `Pi::Config` ask for
194  // `v_bus/2*sqrt(2)`, which is past the inscribed circle -- and the scaled pair
195  // keeps the angle, which is the whole reason for scaling rather than clamping.
196  // 限幅器，用真正需要它的那对数展示。两轴各贴着 `current_pi_config()` 写进
197  // `Pi::Config` 的每轴钳位，合成矢量就是 `v_bus/2*sqrt(2)`，已经出了内切圆——
198  // 而按比例缩放后的那对数保住了角度，这就是"缩放而不是钳位"的全部理由。
199  const float per_axis = 0.5F * kVBusV;
200  const foc::core::Dq<float> over{per_axis, per_axis};
201  const foc::core::Dq<float> held = limit_vector(over, kVCeilingV);
202  std::printf(
203      "\nthe vector ceiling, on a pair that reaches it:\n  asked       |v| = "
204      "%.4f V  angle = %+.1f deg\n  commanded   |v| = %.4f V  angle = %+.1f "
205      "deg\n",
206      static_cast<double>(std::sqrt((over.d * over.d) + (over.q * over.q))),
207      static_cast<double>(std::atan2(over.q, over.d) * 57.29577951308232),
208      static_cast<double>(std::sqrt((held.d * held.d) + (held.q * held.q))),
209      static_cast<double>(std::atan2(held.q, held.d) * 57.29577951308232));
210  return 0;
211}

Two rows of that output are worth reading before the rest:

  • on the machine as shipped (i_d_per_speed_a_s_per_rad left at zero) the MTPA policy answers exactly what the d = 0 policy answers. That is not a bug and not a coincidence: the field's default refuses d current, because a d current is only safe once somebody has stated how the angle is measured.

  • at the top of the sweep the q answer is slightly below the request, because the request does not fit |i| <= i_max and the policy walks down the MTPA curve instead of scaling both components. Scaling both would leave the curve and lose more torque than necessary.

1.1.4.3. Where the numbers come from

Every gain in the example comes from the nameplate, through the library's own rule: foc::current_pi_config(motor_config, bandwidth, v_bus) returns a proportional term that is twice the bandwidth times the inductance less the resistance (floored at zero) and an integral term that is the bandwidth squared times the inductance. The example calls it rather than retyping it -- a second copy of a tuning law is a second law, and it drifts -- which is what the C path, the SIL bench and a board should all do. The feedforward terms are built from the same nameplate through foc::feedforward_config(motor_config).

One property of the returned configuration is worth stating rather than leaving to be found: it is a single gain pair derived from ld, given to both axes. On an interior machine lq is the larger of the two, so the q axis is tuned as if its inductance were the smaller one and lands slightly slower than the d axis at the same requested bandwidth. Two axes that want different gains are two configurations built from the same nameplate; the helper returns one because one is what a symmetric pair of loops needs.

The one field that has no nameplate source is i_d_per_speed_a_s_per_rad. It is a statement about how the angle is measured, so it cannot be derived; the field's own documentation carries the measured numbers for the nominal machine and says which values are safe with and without a position sensor.

1.1.4.4. How it goes wrong

  1. MTPA that silently equals d = 0. Leave the d-current allowance at its default and everything compiles, runs, and produces the surface-machine answer on an interior machine. The library cannot warn: it has no way to know whether the zero is a decision or an omission. This is why the allowance is an explicit field rather than a derived one.

  2. The ceiling inside the PI. Clamping the PI output to the linear range and then adding feedforward can exceed what the modulator can deliver, and the clamp that was supposed to stop the integral from winding up no longer describes the voltage being applied. Clamp the sum -- and clamp the pair, not each axis: two axes each inside their own bound are still a vector outside the circle, and it has rotated away from the reference.

  3. Feedforward on the reference instead of the measurement. The terms are omega * L * i and omega * psi_f; with the reference in place of the measured current the term stops responding when the loop is saturated, which is exactly when it matters.

  4. A d-axis reference the current limit cannot honour. The policy walks down the curve for this reason; a hand-written i_d that ignores the limit produces a pair whose magnitude exceeds i_max and the loop then chases a reference the hardware will never reach.

1.1.4.5. Evidence

Four claim rows cover this page, one per piece: foc/core/reference.hpp, foc/core/limits.hpp, foc/core/pi.hpp and foc/core/feedforward.hpp. The level this page may state is the minimum of those four, and the level itself is read from the claim table in the project README.md rather than written here -- a number copied into a page is a second source of truth with a shelf life.

Not claimed by this page: the torque the loop produces. A torque figure needs a machine model, which is the SIL bench's job and carries its own claim rows. This page stops at the current reference and the voltage command, which is where the library stops too.
