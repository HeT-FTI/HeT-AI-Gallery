c-api

The frozen C11 surface, in include/foc/api/foc_api.h. It is not a second implementation: every entry point runs the same core as the C++ templates, and Consuming the library from outside C++ proves that two doors give the same numbers, tick by tick.

What "frozen" means here, concretely

Rule

Consequence for you

Every fallible function returns foc_err_t and is FOC_WARN_UNUSED

ignoring a status is a compiler warning, and the project's own build treats it as an error. (void) does not silence it on GCC; bind first (foc_err_t e = …) — the escape exists and is deliberately the more typing

Handles are opaque and generation-checked

a stale handle answers FOC_ERR_PARAM instead of dereferencing freed memory. A use-after-free becomes a return value

Structs carry struct_size and fields are only appended

an older caller keeps working; a newer field is not read rather than read out of somebody's stack. A field that cannot be left unset answers FOC_ERR_NOT_IMPL

The pool is static and small

FOC_ERR_NO_RESOURCE is a real answer, not a memory-exhaustion symptom. You are told when the last slot is in use

_f64 variants exist for the commands

a double command from a script keeps its bits; the float form is the one an embedded caller wants

Status codes

Code

Meaning, and what to do about it

FOC_OK

done

FOC_ERR_PARAM

a null argument, an uncovered struct_size, an unconfigured policy, or a request the machine cannot satisfy. Fix the caller

FOC_ERR_NO_RESOURCE

the handle pool is exhausted. Release something

FOC_ERR_STATE

the call does not apply to this state (command before enable, for instance). Read the state machine, not the code

FOC_ERR_NOT_IMPL

this host cannot answer that — a missing callback, or a field this build does not read. Not a caller error, and the distinction is deliberate

FOC_ERR_FAULT

a latched fault is blocking the call. Diagnose, then clear

What they are for

foc_motor_set_observer

foc_motor_destroy

output on and off. disable leaves the stage safe before it returns

foc_motor_clear_fault

foc_tick(motor, dt_s)

Commands

foc_set_speed / foc_set_speed_f64, foc_set_torque / foc_set_torque_f64, foc_set_position / foc_set_position_f64, and foc_set_command for the case where the mode and the reference must change in the same period.

The session shapes are the same in all of them — create, feed, ask, finish, destroy — and the handles are the same kind: a slot with a generation, so a session that was not destroyed is detectable rather than invisible.

The commissioning record

foc_commissioned_set_encode and foc_commissioned_set_decode are the two functions that turn the numbers a commissioning run measures into bytes and back. They are in the C face on purpose: on a serial-numbered production line the thing that writes the record is usually not the thing that firmware lives in. Encoding refuses an unusable set and a short buffer; decoding names the check that failed and the byte offset, so the answer is "re-measure this number", not "this byte looks odd".

Linking it

The ABI is C, the implementation is C++. Set LINKER_LANGUAGE CXX (or add one empty .cpp), otherwise the link fails on symbols named __cxa_. Installing and toolchains states this as a rule and the honest-limits row on a pure-C consumer states the stronger version: a C consumer without the C++ runtime is not supported.
